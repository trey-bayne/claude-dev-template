# /prj-manage

Audit Docker image versions and dependency file versions for an active project.
Creates or updates a Phase M — Maintenance section in TASKS.md for any outdated or risky items.
Run after all build phases are complete, or periodically to catch version drift.

## Model

**Haiku.** Delegate all steps to a Haiku sub-agent:
- Agent tool, subagent_type: general-purpose, model: haiku
- Pass all steps and rules below as the complete prompt
- If the Agent tool call fails, execute in the current session

---

## When to use

- After all numbered build phases are complete
- When Docker images may be stale (older than 90 days)
- Before upgrading any service
- Periodically (e.g. monthly) to catch version drift

---

## Step 1 — Identify project root and files to check

Run: `pwd`

Establish PROJECT_ROOT. All operations stay within it.

Find dependency files:

```bash
find . -maxdepth 2 \
  \( -name "docker-compose.yml" -o -name "docker-compose.yaml" \
     -o -name "compose.yml" -o -name "package.json" \
     -o -name "requirements.txt" -o -name "go.mod" -o -name "Dockerfile" \) \
  -not -path "./.git/*" | sort
```

Read each file found.

---

## Step 2 — Analyze Docker image versions

Use `docker compose config` to get the fully-resolved compose output (handles env var
substitution, anchors, and aliases). Extract every `image:` line.

Categorize each image:
- **LATEST** — uses `:latest` or no tag (unpinned, risky)
- **PINNED** — uses a specific version tag (e.g. `:7.0`, `:3.12-slim`)
- **DIGEST** — pinned by SHA digest (most stable)

For each image, check the local cache:

```bash
docker images --format "{{.Repository}}:{{.Tag}}\t{{.CreatedAt}}"
```

Find the entry matching each image. Calculate age in days from CreatedAt to today.

Flag each image as:
- **NOT PULLED** — not found locally
- **FRESH** — under 30 days
- **CURRENT** — 30–90 days
- **STALE** — over 90 days

LATEST-tagged images: always flag **RISKY** regardless of age.

Optionally, if network is available, check for upstream version info:

```bash
docker manifest inspect [image:tag] 2>/dev/null | head -5
```

Handle failure gracefully — offline or private registry access will fail. This is
supplemental only. The primary status signal is always local image age.

Build the output table:

```
| Service     | Image              | Tag Type | Local Age | Status   |
|-------------|--------------------|----------|-----------|----------|
| mongodb     | mongo:7.0          | PINNED   | 47 days   | CURRENT  |
| redis       | redis:latest       | LATEST   | 12 days   | RISKY    |
| api         | python:3.12-slim   | PINNED   | 103 days  | STALE    |
```

---

## Step 3 — Analyze dependency files

For each file found in Step 1:

**package.json**: Read dependencies and devDependencies. List all entries.
Flag any using `*`, `latest`, or missing version specifiers as UNPINNED.

**requirements.txt**: List all entries. Flag any line without `==version` as UNPINNED.

**go.mod**: List all `require` entries and their versions.

**Dockerfile FROM lines**: Apply the same LATEST/PINNED/DIGEST categorization.

Output a summary table per file type found.

## Step 5 — Create or update Phase M in TASKS.md

Check if Phase M already exists:

```bash
grep "Phase M" TASKS.md
```

- **If Phase M exists**: append new tasks only after the last existing M.X task.
  Do not overwrite or remove any existing Phase M content.
- **If Phase M does not exist**: create the full section at the bottom of TASKS.md.

Proposed Phase M format:

```
## Phase M — Maintenance: [YYYY-MM-DD]

**Goal:** Update stale and risky dependencies identified on [date].
**Generated by /prj-manage. Run /phase-review before executing.**

### Docker Images
- [ ] M.1 — [service]: update [image:tag] (RISKY: unpinned — pin to a specific version)
- [ ] M.2 — [service]: update [image:tag] (STALE: N days — check for newer version)
[one task per flagged image]

### Dependency Files
- [ ] M.N — [file]: pin [package] to a specific version (currently unpinned)
[one task per unpinned dependency]

### Verification
- [ ] M.N — After updates: docker compose up -d --build to rebuild affected services
- [ ] M.N — Run /phase-test (adapt Category A service health checks for this context)
- [ ] M.N — Commit: "phase M complete — maintenance [date]"
```

Show the proposed content before writing it. Ask:

```
Add this maintenance phase to TASKS.md? [yes / no / edit]
```

- **yes** → write it, commit: `prj-manage: add Phase M maintenance tasks [date]`
- **no** → print the report only, make no TASKS.md change
- **edit** → display the content for the user to modify, confirm before writing

---

## Step 6 — Advisory

Print after Phase M is created (or if the user chose no):

```
⚠️  Before executing maintenance updates:
    1. Run /phase-review — Opus will score the update plan for risks
    2. Phase M uses the normal /phase-run and /phase-test cycle
    3. For LATEST-tagged images: look up the correct pinned version before
       editing docker-compose.yml (check the image's Docker Hub page)
    4. If services handle production data, test updates in a dev environment first
```

---

## Rules

- Never fetch external URLs to check versions. Freshness is assessed from local docker
  images only. `docker manifest inspect` is optional supplemental info — handle failure.
- Never modify docker-compose.yml or any dependency file automatically.
  All changes go to TASKS.md as tasks for human-driven execution via /phase-run.
- Always show the proposed TASKS.md content before writing it.
- If Phase M already exists, append new tasks only — never overwrite existing tasks.
- Commit only if the user confirmed yes.
