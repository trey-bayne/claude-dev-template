## Step 5 — Build the project structure

Using the template files from .template/, the extracted content from the rough files,
and the confirmed/corrected answers, build the following structure:

```
./
├── CLAUDE.md              ← populate from template + extraction + confirmed answers
├── TASKS.md               ← populate from template + phase/task content from rough files
├── PROJECT_BRIEF.md       ← populate from template + rough file content (preserve detail)
├── PERMISSIONS.md         ← populate from template, adapt to this project's stack
├── .env.example           ← generate from all env vars found in rough files + answers
├── .gitignore             ← copy `.template/gitignore.template` to `.gitignore`
│                            (renamed: it is stored with a suffix so it does not
│                            apply to the template repo itself)
├── docs/
│   ├── INDEX.md           ← populate from template, update paths/phase names
│   ├── QUICK_REF.md       ← populate from template + stack + port map from extraction
│   ├── ARCHITECTURE.md    ← populate from architecture content in rough files
│   ├── PHASE_NOTES.md     ← populate from phase detail in rough files (preserve all notes)
│   ├── DECISIONS.md       ← populate from tech decisions in rough files
│   ├── ENV_VARS.md        ← populate from env var content in rough files
│   └── SYSTEM_STATE.md    ← copy from template as a skeleton; filled in later, once
│                            the system exists. docs/INDEX.md links to it, so it must
│                            be created even though it starts mostly empty.
└── .claude/
    ├── settings.json      ← copy from template, add project-specific rules
    ├── hooks/
    │   └── session-start.sh  ← populate service health checks from extraction
    └── commands/
        ├── checkpoint.md         ← always installed
        ├── codebase-review.md
        ├── phase-auto.md
        ├── phase-complete.md
        ├── phase-review.md
        ├── phase-run.md
        ├── phase-test.md
        ├── prj-convert.md
        ├── prj-drift.md
        ├── prj-manage.md
        ├── status.md
        ├── sync-issues.md
        ├── dev-build.md          ← two-branch projects only
        ├── ship.md               ← two-branch projects only
        ├── phase-release.md      ← two-branch projects only
        └── phase-rollback.md     ← two-branch projects only
```

**Population rules:**

- Content from the rough files is preserved and reorganized — not discarded or summarized
  away. If it was in the rough files, it belongs somewhere in the output structure.
- `CLAUDE.md` must stay under 200 lines. If content exceeds that, move the overflow
  to the appropriate docs/ file and add a pointer. Never delete content to hit the limit.
- Phase detail (goals, notes, gotchas) goes in `docs/PHASE_NOTES.md`, NOT in CLAUDE.md.
  CLAUDE.md keeps only the phase overview table.
- The full env var block goes in `docs/ENV_VARS.md`, NOT in CLAUDE.md.
  CLAUDE.md keeps only a pointer.
- Architecture diagrams and data flows go in `docs/ARCHITECTURE.md`, NOT in CLAUDE.md.
  CLAUDE.md keeps only a 3–5 line snapshot.
- Tech decisions table goes in `docs/DECISIONS.md`, NOT in CLAUDE.md.
  CLAUDE.md keeps only a compressed row per component.
- Task lists from the rough files go directly into TASKS.md — do not rewrite or compress
  them, preserve the exact task wording. Do **not** split them into per-phase files: every
  command reads TASKS.md directly, and a pointer-style TASKS.md makes `/phase-complete`
  and `/status` report on an empty task list instead of failing.
- Do not copy the template's own trailing boilerplate tasks ("Commit: phase N complete",
  "Update Resume Here to Phase N+1") into the generated task lists. `/phase-run` already
  makes the phase-complete commit, and advancing `## Resume Here` is `/phase-test`'s job
  on a clean pass — a task that does it early makes `/phase-test` build its plan from the
  next phase's Definition of Done and skip a phase entirely.
- Every `{{PLACEHOLDER}}` in every template file must be replaced. None should remain.
  The full list the command files depend on:

  | Placeholder | Filled with |
  |---|---|
  | `{{PROJECT_NAME}}` | Canonical project name |
  | `{{PROJECT_PATH}}` | Absolute host path (e.g. `/opt/myproject`) |
  | `{{GITHUB_USER}}` / `{{GITHUB_REPO}}` | Repo identity |
  | `{{DEV_BRANCH}}` | Working branch — the single branch name for one-branch projects |
  | `{{STABLE_BRANCH}}` | Promotion target (two-branch projects only) |
  | `{{DEV_URL}}` / `{{PROD_URL}}` | Where each environment is reachable |
  | `{{DEV_REBUILD_COMMAND}}` | Exact command that rebuilds the dev stack |
  | `{{PROD_REBUILD_COMMAND}}` | Exact command that rebuilds prod |
  | `{{COMPOSE_PROFILE_ARGS}}` | Compose profile flags, or **empty** for most projects |
  | `{{PROMOTION_COMMAND}}` | What `/phase-auto` must never run — usually `/ship` |
  | `{{SOURCE_FILE_LISTING_COMMANDS}}` | `find` commands listing this project's source files |
  | `{{REVIEW_DOMAINS}}` | `/codebase-review` domain blocks — see the comment in that file |
  | `{{STACK_SPECIFIC_TESTS}}` | `/phase-test` Categories B–E — see the comment in that file |
  | `{{PROJECT_SPECIFIC_PERMISSION_NOTES}}` | Extra permission rationale for this stack |
  | `{{SERVICE_HEALTH_CHECKS}}` | `check_service` lines in the session hook, one per service |

  The remaining placeholders live in the doc templates rather than the commands
  (`{{ARCHITECTURE_SNAPSHOT}}`, `{{CONSTRAINT_N}}`, `{{COMPONENT}}`/`{{DECISION}}`/`{{REASON}}`,
  `{{PHASE_N_NAME}}`/`{{PHASE_N_GOAL}}`, `{{TASK}}`, `{{FIRST_TASK}}`, `{{STARTING_NOTES}}`,
  `{{SERVICE}}`/`{{PORT}}`/`{{TUNNEL_PORT}}`, `{{STANDARD_N}}`, `{{COMMAND_RULE_N}}`,
  `{{PURPOSE_ONE_PARAGRAPH}}`, `{{TODAYS_DATE}}`, `{{COMMIT_MESSAGE}}`,
  `{{FIRST_PENDING_DECISION}}`). They are filled from the Step 3 extraction answers; the
  Step 6 grep is what catches any left behind.

- `TASKS.md` must contain the **Phase Index table** (Phase / Name / Tasks file / Status /
  Release), populated with one row per phase. `/phase-release` reads its Release column —
  without the table that command is inert. Leave Release as `—` for non-release phases.
- `{{REVIEW_DOMAINS}}` and `{{STACK_SPECIFIC_TESTS}}` are the two placeholders that need
  real authoring rather than substitution. Each file carries an HTML comment with the
  shape to follow and a starting point. Do not leave either as a stub that silently
  passes — a test that cannot execute reports as a phase failure forever.
- **Non-Docker projects:** eight commands assume a Docker Compose stack —
  `/status`, `/phase-complete`, `/phase-review`, `/phase-test`, `/codebase-review`,
  `/prj-manage`, `/phase-release`, `/phase-rollback`. If this project is serverless or
  runs some other way, replace the `docker compose ps` health checks and the deploy
  commands with this project's real equivalents while generating those files. Do not
  leave them in place — a command that always errors trains the user to ignore it.
  Also revisit `.claude/settings.json`: the baseline denies `npm`, `npx`, `pip` and `pip3`
  on the principle that nothing installs on the host. That is right for a containerized
  project, where builds run via `docker compose run`, but it hard-blocks an ordinary Node
  or Python project from running its own build and test commands. Adjust the deny list to
  match how this project actually builds, and record the change in `PERMISSIONS.md`.
- **Single-branch projects:** delete the Promotion workflow section from `CLAUDE.md` and do
  not install `/dev-build`, `/ship`, `/phase-release` or `/phase-rollback`. In
  `phase-auto.md`, the Stage 0 branch check should require `{{DEV_BRANCH}}` (the project's
  one branch), and `{{PROMOTION_COMMAND}}` becomes "any deploy command".
- `session-start.sh` must be made executable: `chmod +x .claude/hooks/session-start.sh`

## Step 6 — Validate

After building all files:

1. Count the lines in CLAUDE.md. If over 200, identify what to move and move it.
2. Search all generated files for any remaining placeholder:
   ```bash
   grep -rE '\{\{[A-Z][A-Z0-9_]*\}\}' . \
     --include="*.md" --include="*.sh" --include="*.json" \
     --exclude-dir=".template" --exclude-dir=".git" \
     | grep -vE '\{\{PLACEHOLDERS?\}\}'
   ```
   List any found and either fill them or flag them.

   Match an UPPER_SNAKE name in double braces specifically, not a bare pair of braces.
   Some double braces are supposed to survive: Go template syntax in the session hook
   (the `.Names` format string) and in `/prj-manage` (`.Repository` and `.Tag`), plus
   the literal word PLACEHOLDER used in prose by `/prj-drift` and `/prj-convert`.
   Deleting those breaks working commands. Do not write a sample placeholder literally
   in this file either — the same grep runs against it.
3. Verify no doc points at a file that was not created:
   ```bash
   grep -ohE '(docs/|\./)?[A-Z_]+\.md' docs/INDEX.md | sort -u | while read f; do
     [ -f "$f" ] || [ -f "docs/$(basename "$f")" ] || echo "INDEX.md references missing $f"
   done
   ```
   A dangling pointer in `INDEX.md` is worse than a missing file — it sends Claude Code
   looking for context that does not exist.

4. Verify `.claude/settings.json` is valid JSON **and that it registers the session hook**:
   ```bash
   python3 -c "import json; d=json.load(open('.claude/settings.json')); \
     assert 'hooks' in d and 'SessionStart' in d['hooks'], \
       'session hook is NOT registered — it will never run'; \
     print('valid JSON, SessionStart registered')"
   ```
   An executable hook script is not a running hook. Claude Code only invokes hooks that a
   settings file registers, so without this block `session-start.sh` is inert — and
   `CLAUDE.md` tells Claude the hook already reported service health, which would then be
   a claim about nothing.

5. Verify `session-start.sh` is executable **and that the path in `settings.json` points
   at it** — a registered hook with a wrong path fails as silently as no hook at all:
   ```bash
   ls -la .claude/hooks/session-start.sh
   python3 -c "import json,os; c=json.load(open('.claude/settings.json'))['hooks']['SessionStart'][0]['hooks'][0]['command']; \
     print(c, '->', 'EXISTS' if os.path.isfile(c) else 'MISSING — fix the path')"
   ```
6. Verify all commands are present:
   ```bash
   ls .claude/commands/ | wc -l
   ls .claude/commands/
   ```
   Expect **every `.md` file from the template's `.claude/commands/`**, minus the four
   promotion commands if this project is single-branch. Compare against the template
   `.template/` directory from Step 2 rather than a number written here — a hardcoded count
   goes stale every time a command is added:
   ```bash
   diff <(ls .template/.claude/commands/) <(ls .claude/commands/)
   ```
   Any file in the template and missing here must be either installed or deliberately
   omitted (and said so in the report).

7. Verify the Phase Index table exists in TASKS.md and has one row per phase:
   ```bash
   sed -n '/## Phase Index/,/^## Phase 1/p' TASKS.md | grep -E '^\| [0-9]'
   ```
   Print the data rows, not just the heading — a range of a few lines after the heading
   only reaches the explanatory blockquote and would pass on a table that isn't there.

## Step 7 — Clean up and report

1. Remove the `.template/` directory: `rm -rf .template`
2. Remove the original rough .md files that were reorganized into the structure.
   Before removing, confirm each was fully incorporated into the output.
   If this project was bootstrapped from `project-template.zip` rather than a clone,
   also remove the template's own `BOOTSTRAP.md` and `README.md` from the project root —
   they describe the template, not this project, and their placeholder tables will
   otherwise show up forever in `/phase-test`'s placeholder scan.
3. Initialize git **on the branch this project will actually work on.** A bare
   `git init` leaves you on `master` or `main`, and every two-branch command then stops
   on first use because `{{DEV_BRANCH}}` does not exist:
   ```bash
   git init -b {{DEV_BRANCH}}
   ```
   For a two-branch project, create the stable branch as well once there is a commit
   (step 5), so `/ship` and `/phase-release` have something to merge into:
   ```bash
   git branch {{STABLE_BRANCH}}
   ```
4. **Verify the `.gitignore` contract** — now that a repo exists, these checks mean
   something. Run them here, not in Step 6: `git check-ignore` outside a repo exits
   non-zero for "no repo", which is indistinguishable from "not ignored", so the most
   important assertion below silently passes when run too early.
   ```bash
   git check-ignore -q .env && echo "ok: .env ignored" || echo "FAIL: .env not ignored"
   for f in CLAUDE.md TASKS.md; do
     git check-ignore -q "$f" \
       && echo "FAIL: $f is ignored — remove it from .gitignore" \
       || echo "ok: $f is trackable"
   done
   ```
   One path per `check-ignore` call: with two paths and `-q` it exits
   `fatal: --quiet is only valid with a single pathname`, and that error reads as "not
   ignored" to a shell `||`, so the check passes for the wrong reason.
   `CLAUDE.md` and `TASKS.md` **must be tracked.** `/phase-complete` commits and pushes
   TASKS.md, `/phase-test` commits it when advancing `## Resume Here`, and `/phase-auto`
   treats each committed TASKS.md as its crash-safety boundary. Ignoring them makes every
   one of those a silent no-op, and a fresh clone of the project has no context at all.
5. Run `git add -A && git commit -m "bootstrap: initial project structure"`, then confirm
   the two context files actually landed in the commit:
   ```bash
   git ls-files --error-unmatch CLAUDE.md TASKS.md >/dev/null \
     && echo "ok: context files committed" || echo "FAIL: context files not committed"
   git ls-files --error-unmatch .env.example >/dev/null 2>&1 \
     && echo "ok: .env.example committed" || echo "note: no .env.example (fine if this project has no env vars)"
   ```
6. **Add the remote, or say plainly that there isn't one.** Several commands push:
   `/phase-complete` step 7, `/dev-build`, `/ship`, `/phase-release`, `/phase-rollback`.
   Their error handling covers a rejected push and a network timeout, but not a missing
   remote — that fails with `fatal: 'origin' does not appear to be a git repository`.
   If the GitHub repo for `{{GITHUB_REPO}}` exists:
   ```bash
   git remote add origin git@github.com:{{GITHUB_USER}}/{{GITHUB_REPO}}.git
   git push -u origin {{DEV_BRANCH}}
   ```
   If it does not exist yet, do **not** invent one. Leave the remote unset and list it as
   an open item in the final report, so the user knows the push steps will fail until
   they create it. Note in the report whether `gh auth status` succeeds as well —
   `/sync-issues` and the session hook's issue section need it.
7. Print a final summary:

  [list any remaining gaps]
